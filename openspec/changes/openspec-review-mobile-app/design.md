## Context

Репозиторий уже использует Kotlin Multiplatform с Compose Multiplatform для Android и iOS, поэтому новое приложение должно укладываться в shared UI и shared domain слой без раздвоения логики между платформами. Пользовательский сценарий начинается с выбора корневой папки, где каждая подпапка является одной OpenSpec-спецификацией и содержит `spec.md`; затем приложение строит колоду review-карточек, сохраняет решения свайпами и в конце показывает статистику по качеству спецификаций.

Входные данные имеют слабую структурную гарантию: markdown соответствует OpenSpec-формату Requirement/Scenario, но папки могут быть разного размера, а при повторном импорте часть требований может измениться. Figma-референсы задают мягкий потребительский визуальный язык, поэтому архитектура должна поддерживать крупные карточки, спокойную светлую палитру, выразительную типографику и понятные жесты без перегрузки.

## Goals / Non-Goals

**Goals:**
- Поддержать импорт локальной коллекции OpenSpec-спецификаций с преобразованием в единый список review-карточек.
- Показывать по одной карточке на Requirement, включая название спецификации, заголовок Requirement, полное описание Requirement и все вложенные Scenario в виде последовательных блоков WHEN/THEN.
- Сохранять результат свайпа для каждой карточки и скрывать уже просмотренные карточки из текущего прохода.
- Давать пользователю повторный проход по всем отклоненным или подтвержденным карточкам без нового импорта.
- Показывать агрегированную статистику по коллекции и по каждой спецификации, включая процент требований, отмеченных как некорректные.
- Обеспечить полезный demo mode до первого пользовательского импорта.

**Non-Goals:**
- Редактирование `spec.md` файлов внутри приложения.
- Автоматическая синхронизация папки со спецификациями через облако или git.
- Семантическая валидация бизнес-логики Requirement beyond manual review.
- Поддержка произвольных markdown-форматов вне структуры Requirement/Scenario OpenSpec.

## Decisions

### 1. Использовать shared Compose UI и shared domain/data слой

Приложение будет реализовано в `composeApp/src/commonMain`, чтобы deck, статистика, фильтры и demo flow работали одинаково на Android и iOS. Платформенно-специфичными останутся только folder picker и файловый доступ.

Альтернативы:
- Полностью нативные экраны для каждой платформы. Отклонено, потому что продукт маленький, а поведение и дизайн почти полностью совпадают.
- Web-first экран в wasm с оберткой. Отклонено, потому что пользовательский сценарий зависит от нативного выбора папки и мобильных жестов.

### 2. Нормализовать импорт в модель `Specification -> RequirementCard -> ScenarioView`

После выбора папки importer сканирует вложенные каталоги первого уровня, ищет `spec.md`, парсит секции `### Requirement:` и связанные `#### Scenario:` блоки, после чего строит доменную модель:
- `ImportedSpecification`: идентификатор спецификации, имя папки, человекочитаемое название.
- `RequirementCard`: стабильный `cardId`, `specId`, краткий заголовок, полное описание, список сценариев.
- `RequirementScenario`: `title`, `whenText`, `thenText`.

Одной карточке соответствует один Requirement. Если у Requirement несколько Scenario, они показываются в центре карточки вертикальным списком компактных WHEN/THEN блоков, а не как отдельные карточки. Это сохраняет пользовательскую модель "свайп оценивает Requirement", которую описал пользователь.

Альтернативы:
- Делать одну карточку на Scenario. Отклонено, потому что тогда оценка Requirement распадается на несколько несвязанных решений.
- Хранить raw markdown и парсить на лету при каждом открытии. Отклонено из-за усложнения фильтрации, стабильных идентификаторов и статистики.

### 3. Привязать историю свайпов к стабильному `cardId`, вычисленному из пути спецификации и содержимого Requirement

Для каждого Requirement будет вычисляться `cardId = hash(specFolderName + requirementTitle + requirementBody + scenarios)`. История свайпов сохраняется как запись:
- `cardId`
- `decision` (`approved` или `rejected`)
- `reviewedAt`
- `reviewSessionId`

Это позволяет:
- не показывать уже просмотренные карточки в активной колоде;
- сохранять решения между перезапусками приложения;
- автоматически считать изменившийся Requirement новой карточкой при следующем импорте.

Альтернативы:
- Использовать только индекс карточки. Отклонено, потому что порядок и количество требований меняются между импортами.
- Использовать только название Requirement. Отклонено, потому что одинаковые заголовки могут повторяться в разных спецификациях.

### 4. Разделить режимы колоды на `unreviewed`, `approved-only`, `rejected-only`

После импорта приложение вычисляет рабочую колоду в зависимости от выбранного режима:
- `unreviewed`: только карточки без сохраненного решения;
- `approved-only`: только карточки с правым свайпом;
- `rejected-only`: только карточки с левым свайпом.

Повторный проход не удаляет прошлую историю, а создает новую review session поверх тех же карточек. На уровне аналитики последним состоянием карточки считается самое свежее решение.

Альтернативы:
- Полный reset всей истории при каждом новом проходе. Отклонено, потому что пользователь теряет накопленные выводы.
- Дублировать карточки для replay. Отклонено, потому что это усложняет аналитику и состояние UI.

### 5. Считать аналитику на уровне коллекции и каждой спецификации

Статистика будет рассчитываться из последнего решения по каждой карточке и включать:
- общее число карточек;
- число просмотренных карточек;
- число `approved` и `rejected`;
- completion rate;
- rejection rate по всей коллекции;
- breakdown по каждой спецификации: количество требований, количество отклоненных, процент отклонения.

Это напрямую отвечает на ключевой вопрос пользователя: какие спецификации не соответствуют ожиданиям и в каком проценте.

Альтернативы:
- Показывать только абсолютные значения. Отклонено, потому что процент нужен для сравнения спецификаций разного объема.
- Считать статистику только внутри конкретной review session. Отклонено, потому что пользователь хочет видеть итоговое состояние коллекции.

### 6. Встроить demo source как fallback-коллекцию

Если пользователь еще не импортировал папку, приложение использует встроенную коллекцию `demo-specification` с примером OpenSpec из запроса. Demo collection хранится как bundled asset и проходит через тот же parser/import pipeline, что и пользовательские файлы.

Альтернативы:
- Отдельный hardcoded экран без реального парсинга. Отклонено, потому что он не проверяет основную механику продукта.

## Risks / Trade-offs

- [Нестандартный markdown в `spec.md`] → Парсер должен пропускать неподдерживаемые блоки и импортировать только корректно распознанные Requirement/Scenario; ошибки нужно показывать мягко, без падения приложения.
- [Выбор папки отличается на iOS и Android] → Абстрагировать picker и файловый доступ через платформенный интерфейс, а доменную логику оставить общей.
- [Изменение текста Requirement ломает связь с предыдущим свайпом] → Использовать content-based `cardId` сознательно, чтобы измененное требование считалось новой единицей для ревью.
- [Большие коллекции могут дать слишком длинную карточку] → Центр карточки сделать прокручиваемым, а список сценариев компактным и визуально сгруппированным.
- [Replay поверх прошлой истории может запутать пользователя] → Явно обозначать активный фильтр и использовать last-decision модель для статистики.

## Migration Plan

Изменение вводит новый продуктовый поток поверх существующего шаблона проекта и не требует миграции внешних пользователей или серверных данных. Если появится более сложная схема локального хранения, достаточно будет выполнить локальную миграцию версии базы/хранилища без влияния на формат исходных `spec.md`.

## Open Questions

- Нужно ли в первой версии позволять повторный импорт из нескольких корневых папок или достаточно одной активной коллекции за раз.
- Нужно ли показывать причину отклонения Requirement, или в первой версии достаточно только бинарного свайпа.
- Должна ли аналитика учитывать историю по сессиям, или пользователю нужен только текущий итоговый статус каждой карточки.
